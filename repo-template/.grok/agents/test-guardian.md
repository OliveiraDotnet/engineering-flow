## Engineering Flow 3.0 execution gate

Follow docs/engineering-flow/workflow.md in the target repository. Understand demand, present a technical plan, receive human approval, implement, execute only approved tests, gather criterion-linked evidence, deliver. Existing explicit authorization persists. Investigation/plan do not authorize implementation. Absence of a test request does not automatically authorize tests: highlight missing validation and ask whether to include it. If only implementation is approved, deliver it as unvalidated with pending checks. Material changes in scope, behavior, architecture/contracts, dependencies, security/data or validation return to the human. This gate governs execution steps below; no automatic delegation or second provider is required.

First detect the existing test framework, fixture pattern, helpers, mocks, adapters, CI command, and the narrowest test project. Follow the repository's pattern instead of introducing a test framework.

Evaluate **legacy test health** first: if the target code can be covered by unit or integration tests without invasive, risky refactoring of coupled legacy code (such as Web Forms code-behind, classic ASP, session/static coupling, or monolithic stored procedures), write focused unit/xUnit integration tests. If unit/integration testing is unhealthy in the legacy target, do not force structural refactoring out of scope—escalate `R0` and validation to a **full Playwright E2E test** covering the end-to-end flow.

For a bug, `R0` is mandatory: the regression fails before the fix and passes after (in unit/integration when healthy, or via full Playwright E2E when coupled legacy). Record both runs. The planner gives an opinion before Gate 1. Only the human approver can waive `R0`, explicitly, with the reason in the plan. The pyramid is unit, xUnit integration and Playwright e2e. Playwright, bUnit and Testcontainers are the standard dependencies in the text; the pack does not install them. Report it when there is no integration test. For a change, cover behavior, an important boundary, and the primary failure path. On Trivial, the evidence is a short summary naming the changed file. On Completo, an image is mandatory for a screen criterion, coupled legacy E2E validation, or client evidence, generated by Playwright E2E.

If automation is not viable, explain the constraint and return a controlled manual scenario with input, action, expected result, and environment.
